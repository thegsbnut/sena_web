# Slip AI Check — ผู้ช่วยตรวจสลิปด้วย Cloudflare Workers AI

วันที่: 2026-11-12 · สถานะ: **รอเจ้าของโปรเจกต์รีวิว** (ยังไม่มีโค้ด)

## 1. เป้าหมาย

ให้ AI อ่านสลิปที่ผู้เล่นแนบ แล้วติดป้ายบอก **ผู้จัดเท่านั้น** ว่าสลิปน่าเชื่อถือแค่ไหน
เพื่อให้ผู้จัดรู้ทันทีว่าสลิปใบไหนควรเปิดดูเอง โดยไม่ต้องไล่เปิดทุกใบ

**AI เป็นแค่ผู้ช่วย ไม่ใช่ผู้ตัดสิน:** พฤติกรรมเดิมไม่เปลี่ยน — แนบสลิปแล้วสถานะเป็น `paid` ทันที
(`billing.js` action แนบสลิป) และผู้จัดกด "ให้ส่งใหม่" ได้ตามเดิม

### ถือว่าสำเร็จเมื่อ
- ผู้จัดเปิดหน้าบิลแล้วเห็นป้ายผลตรวจ พร้อมสาเหตุ ข้างผู้จ่ายแต่ละคนที่มีสลิป
- ผู้เล่นไม่เห็นผล AI ในทุกกรณี (รวมถึง response ของ API)
- AI ล่ม ช้า หรือเกินโควตา → การแนบสลิปและการจ่ายบิลทำงานเหมือนเดิมทุกประการ
- ถอดฟีเจอร์ออกได้ 3 ระดับ (ดูหัวข้อ 8)

### ไม่ทำ (non-goals)
- ไม่เปลี่ยนสถานะการจ่ายอัตโนมัติจากผล AI (ไม่ reject เอง ไม่บล็อกการจ่าย)
- ไม่แจ้งผู้เล่นหรือกลุ่ม LINE
- ไม่ตรวจบัญชีผู้รับ (สลิปปิดเลขบัญชีบางหลัก แต่ละธนาคารแสดงไม่เหมือนกัน → ไม่แม่น)
- ไม่ตรวจกับ API ของธนาคาร / ไม่ถอด QR บนสลิป (เก็บไว้เป็นทางเลือกอนาคต ดูหัวข้อ 9)

## 2. การตรวจและป้าย

ตรวจ 3 เรื่อง: **ยอดเงิน · วันที่โอน · สลิปซ้ำ** ถ้าเข้าหลายข้อ แสดงทุกข้อ

| ป้าย | รหัส (`code`) | เงื่อนไข | ข้อความที่ผู้จัดเห็น (ตัวอย่าง) |
|---|---|---|---|
| ✅ ตรวจผ่าน | `ok` | ไม่เข้าข้อใดด้านล่าง และอ่านยอดได้ | ✅ ตรวจผ่าน — ยอด 200 บาท · 12 พ.ย. 69 |
| ⚠️ ยอดไม่ตรง | `amount_mismatch` | ยอดในสลิป ≠ `amount` ของผู้จ่าย (เทียบเป็นสตางค์ ต้องเท่ากันพอดี) | ⚠️ ยอดเงินไม่ตรง — สลิป 120 บาท แต่บิล 200 บาท |
| ⚠️ วันที่ไม่ตรง | `old_date` | วันที่โอน **ก่อน** วันตีแบดของบิล | ⚠️ วันที่ไม่ตรง — สลิปลงวันที่ 3 พ.ย. 69 ซึ่งก่อนวันตีแบด 12 พ.ย. 69 |
| 🚫 สลิปซ้ำ | `duplicate_ref` | เลขอ้างอิงตรงกับสลิปของ **ผู้จ่ายอื่นหรือบิลอื่น** | 🚫 สลิปซ้ำ — ใช้แล้วในบิล 5 พ.ย. 69 ของ สมหญิง |
| ❓ สลิปไม่ชัดเจน | `unreadable` | อ่านยอดไม่ได้ (`amount: null`) หรือไม่ใช่สลิปโอนเงิน | ❓ สลิปไม่ชัดเจน — อ่านยอดเงินไม่ได้ / รูปนี้ไม่ใช่สลิปโอนเงิน |
| ℹ️ อ่านวันที่ไม่ได้ | `date_unreadable` | ยอดอ่านได้ แต่ไม่ได้วันที่หรือแปลงไม่ได้ | ℹ️ อ่านวันที่ไม่ได้ (ไม่ได้ตัดสินเรื่องวันที่) |
| ⏳ ยังไม่ได้ตรวจ | `pending` / `error` | AI ยังไม่เสร็จ ล่ม หรือเกินโควตา | ⏳ AI ตรวจไม่สำเร็จ [ตรวจอีกครั้ง] |

หลักการ:
- วันที่โอน **หลัง** วันตีแบดไม่เป็นปัญหา (ผู้เล่นจ่ายทีหลังได้)
- ref ซ้ำกับ **ผู้จ่ายคนเดิมในบิลเดิม** ไม่นับเป็นซ้ำ (กรณีถูก "ให้ส่งใหม่" แล้วแนบใบเดิม)
- ไม่ติดป้ายเรื่องที่อ่านไม่ได้ → แสดงเป็น "อ่านไม่ได้" ไม่เดา
- ผล AI ที่ **ไม่ผ่านการ validate** ถือเป็น `unreadable` (ดูหัวข้อ 5)

→ ต้องดูผลจริงหลังเปิดใช้ และถือว่า "สลิปซ้ำ" จับได้ไม่ครบทุกเคส (ref ยาวอาจเพี้ยนบางหลัก)

## 4. สถาปัตยกรรม

**แนวทาง A:** ตรวจเบื้องหลังหลังตอบผู้เล่นแล้ว ด้วย `ctx.waitUntil`

```
ผู้เล่นแนบสลิป → billing.js บันทึกสลิป + ตั้ง paid (เหมือนเดิม) → ตอบ {ok:true}
                                    └─ ctx.waitUntil(checkSlip(...))
                                         ├─ readSlip: เรียก Workers AI (binding AI)
                                         ├─ validate + แปลงวันที่ + normalize ref
                                         ├─ หา ref ซ้ำใน slip_checks
                                         ├─ judgeSlip → รายการสาเหตุ
                                         └─ INSERT OR REPLACE ลง slip_checks
ผู้จัดเปิดหน้าบิล → /api/billing (admin) แนบ aiCheck ต่อผู้จ่าย → หน้าเว็บแสดงป้าย
```

### ไฟล์ใหม่ `slip-check.js` (โค้ด AI อยู่ที่นี่ที่เดียว)
- `readSlip(env, bytes, contentType)` → `{ isSlip, amount, dateText, ref }` ดิบจาก AI (ห่อ try/catch, timeout)
- `parseSlipDate(dateText)` → `'YYYY-MM-DD' | null` (ฟังก์ชันล้วน)
- `normalizeRef(ref)` → string สำหรับเทียบ (ฟังก์ชันล้วน)
- `judgeSlip(reading, { amountSatang, billDate, duplicateOf })` → รายการ `{ code, ...ค่าประกอบ }` (ฟังก์ชันล้วน ไม่เรียก AI/DB)
- `checkSlip(env, ctxInfo)` → ทำครบชุดแล้วบันทึก; ไม่ throw ออกนอกฟังก์ชัน
- `slipChecksFor(env, slipKeys)` → map `slipKey → ผลตรวจ` สำหรับหน้าผู้จัด

### จุดที่แตะไฟล์เดิม (4 จุด แต่ละจุดเป็นการเรียกฟังก์ชันสั้นๆ)
1. `worker.js`: ส่ง `ctx` เข้า `billingRoute(req, env, admin, club, ctx)` (ตอนนี้ยังไม่รับ `ctx`)
2. `billing.js` หลังอัปโหลดสำเร็จ (หลัง `updateBill` ผ่านแล้ว): `ctx.waitUntil(checkSlip(...))`
3. `billing.js` ตอนสร้าง view ให้ผู้จัด: แนบ `aiCheck` **เฉพาะเมื่อ `admin` เป็นจริง**
4. `public/billing.js`: แสดงป้าย (เฉพาะ `organizer`) + ปุ่ม "ตรวจอีกครั้ง"

### ค่าตั้งค่า (`wrangler.jsonc`)
- `"ai": { "binding": "AI" }`
- var `SLIP_AI_ENABLED` (`"true"`/`"false"`, ปิดเมื่อไม่ตั้งค่า = ไม่เรียก AI และไม่แสดงป้าย)
- var `SLIP_AI_MODEL` (ค่าเริ่มต้น `@cf/meta/llama-4-scout-17b-16e-instruct`)
- ไม่ต้องเพิ่ม secret

## 5. การเรียก AI และการ validate

**Prompt** สั่งให้ตอบ JSON อย่างเดียว: `{ is_transfer_slip, amount, date_text, ref }`
- `amount` = ยอดโอน (ไม่ใช่ค่าธรรมเนียม) เป็นตัวเลขบาท
- `date_text` = วันที่ **ตามที่พิมพ์บนสลิปตัวต่อตัว** (ห้าม AI แปลงเอง)
- `ref` = เลขอ้างอิงรายการ ถ้ามีหลายเลขให้เลือกเลขที่ยาวที่สุด
- อ่านไม่ได้ให้ `null`; ไม่ใช่สลิปให้ `is_transfer_slip:false`
- `temperature: 0`, `max_tokens` ~300

**Validate ก่อนใช้ (ไม่เชื่อ AI ตรงๆ):**
- parse JSON ไม่ได้ / ฟิลด์ผิดชนิด → `unreadable`
- `amount` ต้องเป็นตัวเลข > 0 และไม่เกินเพดานที่สมเหตุสมผล (เช่น 1,000,000) ไม่งั้นถือว่าอ่านไม่ได้; แปลงเป็นสตางค์ด้วย `Math.round(x*100)`
- `ref` ต้องผ่านเกณฑ์ตามหัวข้อ 6 ไม่งั้นไม่นำไปหาสลิปซ้ำ (แต่ยังเก็บค่าที่อ่านได้ไว้แสดง)
- ภาพที่ส่ง: ใช้รูปเดิมที่อัปโหลด (ไม่เกิน 1 MB, JPG/PNG/WebP) → ส่งเป็น data URI

## 6. กฎแปลงวันที่และเลขอ้างอิง

**วันที่ (`parseSlipDate`)** — จากสลิปจริงที่ทดสอบ รูปแบบที่ต้องรองรับ:
`01 ม.ค. 2567 12:00:00` · `25 Mar 25, 13:13` · `02 พ.ย. 2565 - 11:34` · `10 Nov 2026 12:29:04` · `12 พ.ย. 69 11:30 น.` · `10 พ.ย. 69, 12:13 น.`
- เดือนไทย (เต็ม/ย่อ) → ปีเป็น **พ.ศ.**; เดือนอังกฤษ (เต็ม/ย่อ) → ปีเป็น **ค.ศ.**
- ปี 2 หลัก: พ.ศ. → `2500 + yy`; ค.ศ. → `2000 + yy`
- รองรับรูปแบบตัวเลข `dd/mm/yyyy` โดยปี > 2400 ถือเป็น พ.ศ.
- **sanity check:** ปี ค.ศ. ที่แปลงได้ต้องอยู่ในช่วงปีปัจจุบัน −2 ถึง +1 ไม่งั้น → `null` (อ่านวันที่ไม่ได้)
- แปลงไม่ได้ → `null` → ป้าย `date_unreadable` ไม่ใช่ `old_date`
- วันตีแบดของบิลใช้ `billDate(bill)`; เทียบเป็นวันที่ตามเวลา Asia/Bangkok

**เลขอ้างอิง (`normalizeRef`)**
- ตัดช่องว่างและขีด, ไม่สนตัวพิมพ์เล็กใหญ่, นับ `I`/`l`/`1` เป็นตัวเดียวกัน และ `O`/`0` เป็นตัวเดียวกัน
  (สลิป SCB มี `IlId` ที่ AI อ่านสลับได้ — ใน spike ผ่านเมื่อ normalize)
- นำไปหาสลิปซ้ำ **เฉพาะเมื่อ** normalize แล้วยาว ≥ 10 ตัว และไม่ใช่ตัวซ้ำล้วน (กัน ref สั้น/เดา เช่น `00000000…`)
- สลิปกรุงเทพมี 2 เลข (Bank ref สั้น + Transaction ref ยาว) → prompt สั่งเอาเลขยาวสุด

## 7. ข้อมูล

ตาราง `slip_checks` ใน `DB` สร้างแบบ lazy (`CREATE TABLE IF NOT EXISTS`) ตามแนวโมดูลอื่น

```sql
slip_checks (
  slip_key    TEXT PRIMARY KEY,  -- ตรงกับ slipKey ของผู้จ่าย
  club        TEXT NOT NULL,
  bill_id     TEXT NOT NULL,
  payer_id    TEXT NOT NULL,
  state       TEXT NOT NULL,     -- 'pending' | 'done' | 'error'
  labels      TEXT,              -- JSON รายการสาเหตุ [{code,...}]
  read_amount INTEGER,           -- สตางค์
  read_date   TEXT,              -- YYYY-MM-DD (ค.ศ.) หลังแปลง
  read_ref    TEXT,              -- ref ดิบที่ AI อ่านได้
  ref_norm    TEXT,              -- ref หลัง normalize (ใช้หาซ้ำ)
  model       TEXT,
  checked_at  INTEGER
)
INDEX ON (ref_norm)
```

- **ไม่แตะ payload บิลและไม่เพิ่ม `revision`** — ผล AI เป็นข้อมูลอนุพันธ์ ผลซ้ำได้ผลเดิม จึงใช้
  `INSERT OR REPLACE` ได้โดยไม่ขัดกับกฎ optimistic concurrency ของข้อมูลหลัก
- แนบสลิปใหม่ (ถูก "ให้ส่งใหม่") → `slipKey` ใหม่ → แถวใหม่; แถวของ key เก่าลบตอนลบสลิปเก่า
- `prunePaidSlips` ลบรูปแล้ว **เก็บแถว `slip_checks` ไว้** เพื่อตรวจซ้ำย้อนหลัง และลบแถวที่เก่ากว่า 180 วันใน cron เดิม

## 9. ความผิดพลาดและข้อจำกัดที่ต้องรู้

- `checkSlip` ห่อ try/catch ทั้งหมด; ล้มเหลว → `state='error'` + `logError`, **ไม่กระทบการอัปโหลด**
- ไม่ลองใหม่อัตโนมัติ; ผู้จัดกด "ตรวจอีกครั้ง" ได้ (ขึ้นเมื่อ `error` หรือ `pending` นานกว่า 2 นาที)
- งานใน `waitUntil` มีเวลาจำกัด; เกินเวลา → ถือเป็น `error`
- สลิปซ้ำจับได้ไม่ครบ (ref ยาวอาจเพี้ยน) — เป็นป้าย "ช่วยเตือน" ไม่ใช่หลักฐาน
- ภาพถ่ายหน้าจอจริงอาจแม่นน้อยกว่าสลิปตัวอย่างที่ทดสอบ
- ค่าใช้จ่าย Workers AI วัดแล้ว ≈ $0.00064 ต่อสลิป (เฉลี่ย ~58 neurons; ดู `HANDOFF.md`); โควตาฟรี 10,000 neurons/วัน (~170 สลิป) ทั้งแผน Free และ Paid ยืนยันจากหน้าราคาของ Cloudflare แล้ว เกินโควตาบนแผน Free → คำขอล้มเหลว (โค้ดรองรับเป็นสถานะ error)
- ทางเลือกอนาคต (นอก scope): ถอด QR "สแกนตรวจสอบ" บนสลิปเพื่อได้ ref ที่แม่นกว่าการอ่านตัวหนังสือ

## 10. API

- `GET/POST /api/billing...` เดิม: เมื่อ `admin` → แต่ละผู้จ่ายที่มี `slipKey` มี `aiCheck`:
  `{ state, reasons: [{code, ...}], readAmount, readDate }`; ผู้เล่นทั่วไป **ไม่มีฟิลด์นี้**
- ใหม่: `POST /api/billing?action=slip-check` (admin เท่านั้น, ผ่านเช็ก Origin เหมือน POST อื่น)
  body `{ payer, revision? }` → ตรวจสลิปปัจจุบันของผู้จ่ายใหม่ รอผลแล้วตอบ `{ ok:true }`
  (ไม่เปลี่ยนสถานะการจ่าย ไม่ต้องใช้ revision ของบิล)
- ข้อความป้ายภาษาไทยสร้างฝั่งหน้าเว็บจาก `code` + ค่าประกอบ (ปรับถ้อยคำได้โดยไม่แตะ logic)

- ใต้บรรทัดสถานะของผู้จ่ายที่มีสลิป: ป้ายตามตารางหัวข้อ 2 หนึ่งบรรทัดต่อสาเหตุ แสดงเมื่อ `organizer` เท่านั้น
- ✅ สีจาง; ⚠️/🚫 สีเตือนพร้อมค่าที่อ่านได้; ❓ บอกให้เปิดดูเอง; ⏳ มีปุ่ม "ตรวจอีกครั้ง"
- การ์ดสรุป (เฉพาะผู้จัด): `🤖 มีสลิปที่ควรตรวจ N ใบ` เมื่อมีสลิปที่เข้า ⚠️/🚫/❓
- ไม่มีปุ่มใหม่ที่เปลี่ยนสถานะการจ่าย — ผู้จัดใช้ "ดูสลิป" / "ให้ส่งใหม่" ตามเดิม
- ข้อความทุกอันต้องผ่าน `escape()` ก่อนใส่ `innerHTML`

## 12. แผนเทส (`test-slip-check.mjs`, เพิ่มใน script `test` ของ `package.json`)

ใช้ AI จำลอง ไม่ยิง Cloudflare จริง ตามแนว D1/LINE จำลองของโปรเจกต์

- `judgeSlip`: ยอดตรง / ไม่ตรง / ต่างแค่สตางค์ / วันที่ก่อนวันตีแบด / วันที่เท่ากับ / หลัง / อ่านวันที่ไม่ได้ / ref ซ้ำต่างบิล / ref เดิมผู้จ่ายคนเดิม / หลายป้ายพร้อมกัน
- `parseSlipDate`: 6 รูปแบบจากสลิปจริง + `dd/mm/yyyy` พ.ศ./ค.ศ. + ข้อความขยะ + ปีนอกช่วง
- `normalizeRef`: `IlId`↔`I11d`, ตัวพิมพ์เล็กใหญ่, ช่องว่าง/ขีด, สั้นเกินไป, ตัวซ้ำล้วน
- validate ผล AI: JSON เสีย, ยอดติดลบ/ศูนย์/เกินเพดาน, ชนิดข้อมูลผิด, ตอบเป็นข้อความแทน JSON
- integration: แนบสลิป → มีแถว `slip_checks`; AI throw → สลิปยังเป็น `paid` และ `state='error'`;
  `SLIP_AI_ENABLED=false` → ไม่เรียก AI; **ผู้เล่นไม่เห็น `aiCheck` แต่ admin เห็น**; `slip-check` ต้องเป็น admin และผ่านเช็ก Origin
- เทสเดิมใน `test-billing.mjs` ต้องผ่านทั้งหมดโดยไม่แก้ (ยืนยันว่าถอดออกปลอดภัย)
- ก่อนส่งงาน: `npm run format`, `npm test`, `npm run build` ต้องผ่าน

## 13. ลำดับการทำ

1. รีวิว spec นี้ → เขียนแผนงาน (writing-plans) → เลือกวิธีลงมือ
2. ทำใน branch เดียว, commit เล็กๆ, ตรวจโค้ด AI ที่ทดสอบได้ด้วยเทสจำลองก่อนต่อ UI
3. ก่อน merge: ตรวจค่าใช้จ่าย/โควตา Workers AI และลองกับสลิปจริงของก๊วนอย่างน้อยไม่กี่ใบ
4. merge เข้า `main` เป็นก้อนเดียวเมื่อเจ้าของโปรเจกต์สั่ง
